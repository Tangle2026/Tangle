A new transaction architecture for a network where value can move through layers of routing, fragmentation and confidential state.

TANGLE is a proposed privacy-oriented Layer-1 network designed around randomized multi-stage routing, recursive transaction fragmentation, protocol-native Routing Vaults and cryptographic mechanisms intended to reduce transaction correlation.

01 · ABSTRACT

Changing how a transaction is represented.

Public blockchains expose a powerful but highly observable transaction graph. TANGLE explores a different approach: instead of making privacy a feature added on top of a conventional transfer, the protocol changes the way value is represented and routed.

A transaction can be transformed into multiple fragments, recursively split, wrapped in cryptographic routing layers and distributed across dynamically selected routing capacity. The final recipient receives the intended value without the network needing to represent the entire transaction as one simple public edge.

02 · THE PROBLEM

The transaction graph is the product.

On transparent networks, transaction history is permanent. Addresses, transfers, balances, timing relationships and repeated behavioral patterns can become a durable source of information.

01 · Visibility

Public relationships

02 · Metadata

Timing & patterns

Even when addresses are pseudonymous, timing, amounts and behavioral patterns can provide additional correlation signals.

03 · Architecture

Privacy after the fact

Adding a privacy layer to an existing transaction model can leave fundamental architectural assumptions unchanged.

TANGLE's response

Move the privacy boundary inward. The protocol should operate on commitments, fragments, routing instructions and proofs rather than requiring every routing participant to understand the complete transaction.

07 · RECURSIVE SPLITTING

One transaction can become a tree.

Recursive splitting allows the protocol to transform one transaction value into a hierarchy of smaller fragments. The objective is to reduce the informational value of any individual fragment.

Illustrative fragment tree
Transaction │ ├── Fragment A │ ├── A1 │ ├── A2 │ └── A3 │ ├── Fragment B │ ├── B1 │ └── B2 │ └── Fragment C ├── C1 ├── C2 └── C3
Parameter Proposed Direction Purpose
Maximum fragment share ≤ 50% of stage value Reduce the dominance of a single fragment.
Minimum fragment target 0.001 Provide a lower routing granularity target.
Minimum transfer $1 equivalent Prevent economically meaningless micro-transactions.
Recursive depth Dynamic Adapt fragmentation to transaction size and network conditions.
Important:

These parameters are proposed protocol targets, not claims of cryptographic guarantees. Final values should be determined through simulation and formal security analysis.

Finalized fragmentation rules

At the start of each transaction, the protocol randomly chooses a target final fragment count between 100 and 1000. The source is not instantly converted into that number. Fragments grow recursively: a branch may produce 1–10 child fragments per Split, and child values may be unequal. The protocol randomly decides Split or Pass-through. After each Split, each resulting fragment may be sent to Routing or Pool according to protocol randomness. Pool residence duration is randomly selected in blocks. A fragment may enter Pool repeatedly without a protocol-level one-time limit. After reaching the target final fragment count and completing the routing process, fragments enter recombination and settlement.

08 · PRIVACY MODEL

Privacy by architecture, not by promise.

TANGLE does not define privacy as absolute invisibility. Its objective is to make transaction relationships substantially harder to correlate under the protocol's assumptions.

Layer 01

Value confidentiality

Amounts can be represented through commitments and protected transaction objects.

Layer 02

Fragment confidentiality

Individual routing participants should only receive the information necessary for their local transition.

Layer 03

Route separation

No single Routing Vault should need to know the complete transaction route.

Privacy boundary

Cryptography cannot automatically eliminate network-level timing analysis, endpoint metadata, wallet compromise, traffic observation or implementation bugs. TANGLE therefore treats privacy as a system property spanning cryptography, routing, networking and wallet behavior.

12 · PROOF OF ROUTING

Proof of Routing turns routing into a verifiable protocol primitive.

Proof of Routing (PoR) is TANGLE's cryptographic mechanism for proving that a Routing Vault received an assigned protected fragment, executed the protocol-defined local routing transition, produced a valid successor state and submitted the result for deterministic verification. PoR is not the consensus mechanism: it is the proof layer that makes routing work verifiable and economically accountable.

Core principle

A Vault is never rewarded merely for being online or for claiming that it routed a fragment. Reward eligibility begins only after the network accepts a valid Proof of Routing bound to a specific routing task and state transition.

12.1 · What PoR proves

For every routable fragment transition, the protocol creates a unique routing task. The Vault must produce a proof that binds the task, the input fragment state, the required operation and the resulting state. The proof establishes correctness of the protocol transition without requiring the Vault to learn the protected transaction amount, sender, recipient or complete route.

01 · INPUT AUTHENTICITY

Correct fragment

The proof binds the Vault's work to the fragment commitment and routing task assigned by the protocol. A proof for an unrelated fragment cannot be reused.

02 · OPERATION CORRECTNESS

Correct operation

The proof establishes that the Vault executed the operation encoded by the task: PASS, SPLIT, POOL or another protocol-defined routing transition.

03 · STATE TRANSITION

Valid successor state

The output commitment, encrypted payload and routing metadata must form a state that satisfies the transition rules for the assigned operation.

04 · CONSERVATION

Value conservation

Where the operation changes fragment structure, the proof can establish the required commitment relation and conservation rule without exposing the underlying value.

05 · FRESHNESS

Fresh task

Task nonce, epoch and anti-replay state bind the proof to one authorized execution window.

06 · PRIVACY BOUNDARY

No plaintext requirement

PoR is designed so that verification relies on commitments, protected payloads and proofs rather than requiring public transaction plaintext.

12.2 · Routing Task

Before a Vault performs work, TANGLE creates a protocol-bound task. The task is derived from authenticated protocol state and randomness and contains only the information required for the local transition. The complete transaction is not delivered to the Vault.

RoutingTaskᵢ = H( domain || epoch || task_nonce || vault_id || fragment_commitment || operation_code || next_hop_reference || expiry ) The task commits the Vault to one specific routing transition.
Field Purpose Visibility
task_id Unique identifier for the routing task. Vault + protocol
fragment_commitment Binds the task to the expected input fragment state. Protected / commitment
operation_code Specifies PASS, SPLIT, POOL or another permitted transition. Vault-local
next_hop_reference Defines the protocol-selected successor routing destination. Local task data
task_nonce Prevents replay of an old routing task. Protocol-bound
expiry Limits the validity window of the task. Protocol-bound
Privacy boundary

The task is intentionally local. A Vault can know what operation it must perform and where the protected result must be sent, while the protocol prevents the task from becoming a plaintext description of the complete transaction.

12.3 · Proof Statement

PoR is represented as a zero-knowledge proof of a relation between public task/state data and a private execution witness. The exact proving system and circuit are implementation parameters and must be selected and audited during the cryptographic design phase.

Public statement xᵢ = { task_id, epoch, vault_id, C_in, operation_code, C_out, next_hop_reference, expiry, anti_replay_reference } Private witness wᵢ = { protected_fragment_state, commitment_openings, encrypted_payload_state, routing_authority_secret, transformation_witness, operation_randomness, successor_state_witness } PoRᵢ = Prove(R_PoR, xᵢ, wᵢ) Verify(R_PoR, xᵢ, PoRᵢ) → TRUE / FALSE

The witness is never published as part of the proof. A verifier receives the public statement and the proof and checks whether a valid witness exists that satisfies the routing relation.

12.4 · The Routing Relation

The routing relation is the logical rule set that a valid PoR must satisfy. It does not expose the private fragment value; it proves consistency between the committed input, the assigned operation and the committed output.

R_PoR = TaskAuthorized ∧ FragmentMatchesTask ∧ OperationAllowed ∧ TransitionCorrect ∧ CommitmentConsistent ∧ ConservationSatisfied ∧ NextHopAuthorized ∧ NotExpired ∧ NotReplayed where: TaskAuthorized = task is valid for this Vault / epoch FragmentMatchesTask = witness opens to the committed input state OperationAllowed = operation_code is permitted TransitionCorrect = output is the valid result of the operation CommitmentConsistent= C_in and C_out satisfy the required relation ConservationSatisfied= required value conservation holds NextHopAuthorized = successor reference matches protocol rules NotExpired = task is inside its validity window NotReplayed = task / transition has not already been consumed
PASS

Pass-through proof

The proof demonstrates that the protected fragment remained structurally valid while its routing state was advanced to the protocol-selected successor.

SPLIT

Split proof

The proof demonstrates that the child commitments are a valid transformation of the parent commitment and satisfy the protocol's conservation and fragmentation constraints.

POOL

Pool-entry proof

The proof demonstrates that the fragment was committed into the permitted Pool state with a valid transition reference and expiry/residence parameters.

RE-ROUTE

Re-routing proof

The proof demonstrates that a fragment leaving a Pool or routing stage has a valid successor state and is bound to the protocol-selected next routing destination.

12.5 · Blind Routing and Cryptographic Execution

TANGLE's routing model is designed around blind execution. The Vault performs the local transformation on protected fragment state rather than receiving plaintext economic information. Commitments represent confidential values, encrypted payloads protect fragment contents, homomorphic operations can support transformations such as splitting, and ZK proofs attest that the resulting state is valid.

Protected Fragment │ ├── C_in = Commit(value, randomness) ├── encrypted_payload └── routing_instruction │ ▼ Vault-local blind transformation │ ├── C_out ├── encrypted_payload' └── successor metadata │ ▼ PoR circuit │ └── π = Prove(R_PoR, public_statement, private_witness) │ ▼ Network verification

A critical distinction is that a zero-knowledge proof can prove that the protocol's defined transition was executed without revealing protected inputs. It cannot, by itself, prove that a machine never leaked information through arbitrary external side channels. Operational security, encrypted transport, key isolation and implementation controls therefore remain separate security requirements.

12.7 · Proof Package

A routing submission carries the minimum metadata required to verify and commit the transition. The package is designed so that public verification does not require publication of the transaction's private value.

RoutingProofPackage { task_id vault_id epoch C_in operation_code C_out next_hop_reference transition_nonce expiry nullifier_or_transition_id proof }

The exact serialization, signature scheme, proof encoding and aggregation format are implementation parameters. They should be standardized only after the cryptographic circuit and state machine are formally specified.

12.8 · Reward Accounting

A valid PoR creates a routing-work record. One accepted routing transition counts as one unit of valid routing work unless a future protocol specification defines a different weight. The monetary value of the fragment does not determine the work unit.

VaultRewardPool = TransactionFee × 30% Workᵢ = Σ accepted PoR transitions by Vaultᵢ StakeWeightᵢ = √(StakedTGLᵢ) Rewardᵢ = VaultRewardPool × (Workᵢ × StakeWeightᵢ) / Σⱼ(Workⱼ × StakeWeightⱼ)
Economic separation

PoR determines whether routing work was valid and creditable. The reward formula determines how the Vault portion of transaction fees is allocated among Vaults. A larger stake increases economic weight with diminishing returns, but stake alone does not create routing-work credit.

Accountable routing

Routing becomes a state transition that can be objectively accepted or rejected instead of an off-chain promise.

PRIVACY

Minimal disclosure

The verifier can establish correctness from commitments and proofs without requiring the Vault to publish the protected economic state.

ECONOMICS

Proof-backed rewards

Transaction fees can fund Vault rewards while PoR prevents unsupported routing claims from becoming reward-bearing work.

Implementation status

PoR is a protocol design direction in the current whitepaper. The exact ZK proving system, circuit constraints, trusted setup requirements if any, proof aggregation strategy, hardware requirements and benchmark targets remain subjects for formal cryptographic engineering, simulation, adversarial testing and independent audit.

12.11 · Cryptographic Architecture: Nova-Style Folding / IVC

TANGLE adopts a Nova-style folding and incrementally verifiable computation (IVC) architecture as the primary direction for PoR. The reason is architectural: TANGLE is not one monolithic computation. It is a long sequence of bounded routing state transitions in which each fragment moves from one valid state to another. Folding allows the prover to incrementally update a proof of the computation rather than constructing an entirely independent proof for the full history at every step.

Why folding fits TANGLE

Nova is designed around folding schemes and IVC: a prover can carry forward a proof state for a sequential computation, while verification does not grow linearly with the number of executed steps. This maps naturally onto TANGLE's fragment routing model, where a transaction may pass through many independent routing transitions before settlement.

TANGLE PoR chain Initial fragment state │ ▼ PoR Step 1 │ ▼ Fold / IVC update │ ▼ PoR Step 2 │ ▼ Fold / IVC update │ ▼ ... │ ▼ PoR Step N │ ▼ Final / aggregated proof state │ ▼ L1 verification

12.12 · Bounded Proof Steps

The key performance principle is that a Vault should prove a bounded local transition, not the entire transaction. A PASS, SPLIT, POOL or RE-ROUTE operation is represented as a small protocol-defined transition with explicit limits. This prevents a single routing task from becoming an unbounded proving workload.

PASS

Minimal transition

PASS keeps the protected fragment structurally valid and advances routing state. It is intended to be the cheapest PoR operation.

SPLIT

Bounded fan-out

A split may create up to 10 child fragments. The circuit proves the required commitment and conservation relation without revealing child values.

POOL

Bounded Pool transition

Pool entry and exit use explicit state, expiry and residence parameters. The proof does not require the Vault to learn the economic value of the fragment.

12.13 · Mobile-First Vault Target

TANGLE sets a mobile-class device as the minimum hardware target for ordinary Routing Vault participation. This is an engineering target, not a claim that every existing phone will meet the final requirements. The protocol must be designed so that a modern ARM64 smartphone can execute the bounded PoR transition without a GPU or a dedicated server.

Minimum Vault target ARM64 smartphone │ ├── CPU-only proving ├── bounded memory usage ├── bounded witness size ├── no trusted server required └── local key isolation ↓ Small PoR step ↓ Nova-style fold / IVC update ↓ Network acceptance

Mobile ZK proving is technically feasible in principle: existing mobile ZK tooling demonstrates native proof and witness generation on iOS and Android. TANGLE nevertheless requires its own benchmarks because support for a particular proving framework does not guarantee that the TANGLE PoR circuit will fit a phone's CPU, memory, thermal and battery constraints.

12.14 · Vault / Prover Separation

TANGLE separates routing participation from optional proving acceleration. An ordinary Vault must remain capable of producing the standard bounded PoR step itself. Specialized proving infrastructure may aggregate or accelerate proofs, but it must not become a trusted custodian of transaction plaintext or a mandatory intermediary for routing participation.

12.15 · Security vs Performance Boundary

Security must not come from making proofs artificially heavy.

TANGLE does not define cryptographic strength as a function of proving time. Security comes from the soundness and zero-knowledge properties of the selected proof system, correct circuit constraints, commitment binding, nullifier rules, authenticated task assignment and correct state transition logic. Performance optimization should reduce redundant computation while preserving those security properties.

12.16 · Benchmark and Engineering Gate

Before the cryptographic design is frozen, TANGLE must benchmark the real PoR circuit on representative mobile hardware. The benchmark suite must measure proof-generation latency, peak RAM, CPU utilization, proof size, verification latency, energy/thermal behavior, failure rates and throughput under sustained routing load. No final hardware requirement should be presented as guaranteed until these measurements exist.

Engineering gate Circuit implementation ↓ Mobile benchmark ↓ Adversarial workload test ↓ Circuit / protocol optimization ↓ Independent cryptographic review ↓ Production PoR specification

The target is not merely to make one proof run on a phone. The target is to make sustained Vault participation economically and thermally practical without weakening the cryptographic statement being proved.

16 · THREAT MODEL

Design against adversaries.

Sybil attacks

An attacker creates many identities to influence routing selection or network behavior.

Routing manipulation

Malicious participants attempt to bias routing decisions or selectively disrupt fragments.

Timing analysis

Observers correlate packet timing, network activity and settlement events.

Liquidity attacks

Attackers attempt to manipulate protocol liquidity or economically constrain routing capacity.

Replay attacks

Previously valid routing objects are submitted again.

Key compromise

Compromise of spending, routing or withdrawal authority can create different classes of damage.

Security philosophy

TANGLE should assume that some routing participants can be malicious. The system therefore aims to limit what any single participant can learn or corrupt.

23 · APPLICATION & INTEROPERABILITY

An infrastructure layer other protocols can build on — and connect to.

Architecture Proposed / Security Model Under Research

TANGLE is not intended to be only a private payment network. Its long-term architecture includes a native Application Layer for protocols built directly on TANGLE and an Interoperability Layer for connecting existing chains, assets and applications without requiring every external protocol to be rewritten from scratch.

TANGLE ecosystem stack

TANGLE ECOSYSTEM │ ├── Application Layer │ ├── Private DeFi │ ├── Lending / Borrowing │ ├── DEX / Trading │ ├── Stable-value protocols │ ├── Institutional settlement │ └── Privacy-native applications │ ├── Interoperability Layer │ ├── Asset Gateway │ ├── Message Bridge │ ├── Chain-specific Light Clients / Proof Adapters │ ├── Privacy Adapters │ └── Cross-chain SDK │ └── TANGLE L1 Core ├── Routing ├── Fragments ├── PoR / Nova-style folding direction ├── Confidential State ├── Nullifiers ├── Settlement └── Consensus / Validators

Two ways to build

1. Native: a developer deploys protocol logic directly against TANGLE's confidential state, routing, settlement and SDK primitives.

2. Connected: an existing protocol remains on its original chain and uses TANGLE through asset and message interoperability.

This separation is important: TANGLE does not require every protocol to become a TANGLE-native protocol before users can access its infrastructure.

23.2 · How an existing protocol connects

An existing protocol does not need to be rewritten as a TANGLE-native application immediately. The integration is split into a source-chain side, an interoperability adapter and a TANGLE-side application or gateway.

Generic connection flow

Existing Protocol / Chain │ ▼ Source-side Gateway / Adapter │ ▼ Proof / State Verification │ ▼ TANGLE Interoperability Layer │ ├── Asset Gateway ├── Message Gateway └── Privacy Adapter │ ▼ TANGLE L1 │ ├── Confidential State ├── Routing ├── PoR └── Settlement │ ▼ TANGLE Application / User

Step 1 — Source event. The user or protocol creates an operation on the source chain: deposit, message, state change or application call.

Step 2 — Source commitment. The source-side gateway records the operation and produces the data needed to prove that the event really happened under the source chain's consensus/state rules.

Step 3 — Verification. TANGLE verifies the source event using the appropriate chain-specific verification mechanism. Depending on the source network, this may use a light client, Merkle/state proof, validity proof, or another explicitly specified verification adapter. The security model is chain-specific and must be documented rather than hidden behind the word "bridge".

Step 4 — TANGLE representation. Once accepted, the verified event creates a TANGLE-side asset/state representation. For an asset transfer this may be a locked/custodied representation, a protocol-defined wrapped representation, or another mechanism chosen for that asset and bridge model.

Step 5 — Privacy layer. The user can then route the value through TANGLE's fragmentation, confidential-state and Proof of Routing architecture.

Step 6 — Application execution. A TANGLE-native application can use the resulting confidential asset/state without exposing the entire source-chain transaction graph.

Step 7 — Return / exit. When value or a message needs to return to the source chain, TANGLE creates an authenticated exit record. The source-side adapter verifies the required TANGLE proof/state and executes the release, mint/burn, claim or message action according to the asset's bridge policy.

Important: a bridge is not automatically trustless.

TANGLE should prefer proof-based interoperability. A bridge must explicitly define who verifies the source chain, what can be proven, what happens if a chain halts or forks, how replay is prevented, how upgrades are handled and what the maximum loss is under a compromise. A multisig bridge, committee bridge, light-client bridge and ZK-proof bridge have materially different trust assumptions.

23.3 · Asset Bridge

The Asset Bridge moves economic value between an external network and TANGLE. The exact mechanism is asset-specific. A canonical model is lock-and-represent on entry and burn/release on exit, but the protocol should not assume that one bridge design is correct for every asset.

23.4 · Message Bridge

Messages allow an existing protocol to use TANGLE without necessarily moving its entire liquidity. A source-chain application can request a TANGLE action; TANGLE verifies the authenticated message and executes an allowed destination action. The reverse direction follows the same proof-and-replay-protection model.

Example: Bridge-and-Call style flow

User / Protocol on Chain A │ ├── Asset + Message │ ▼ Interoperability Adapter │ ├── Verify source state ├── Verify message └── Create unique message ID │ ▼ TANGLE Message Gateway │ ├── Replay Check ├── Authorization Check ├── Proof Verification └── Privacy / Routing Policy │ ▼ TANGLE Application │ └── Execute requested action

23.5 · Privacy Adapter

The Privacy Adapter is the bridge between conventional public-chain applications and TANGLE's privacy primitives. It does not magically make the source chain private. Instead, it creates a controlled boundary: assets or application state enter TANGLE, privacy-preserving operations occur inside TANGLE, and only the minimum required exit information is exposed when value or messages leave.

What this enables

A lending, trading, treasury or settlement protocol could keep its canonical deployment on an existing chain while using TANGLE as a confidential execution, routing or settlement environment for selected flows. A future version could also deploy a native TANGLE implementation when deeper integration is beneficial.

23.6 · Security Architecture for Interoperability

Light-client verification

Where practical, TANGLE can track a source chain's consensus and verify state proofs instead of trusting a third-party committee.

Proof adapters

For chains with different consensus or execution models, a dedicated adapter defines exactly what proof is accepted and how it maps into TANGLE state.

Replay protection

Every cross-chain message or asset event receives a unique domain-separated identifier and can be consumed only once.

Finality policy

Each connected chain must define finality assumptions, confirmation rules, reorg handling and failure behavior before production integration.

Rate limits

Bridge gateways can enforce configurable exposure limits, per-asset caps and circuit breakers to contain losses during abnormal conditions.

Emergency controls

Emergency pause mechanisms may stop new inbound/outbound operations while preserving already-finalized state, subject to governance and timelock rules.

23.7 · Why this model

Interoperability should be treated as a protocol layer, not as a collection of ad-hoc bridges. Existing interoperability systems demonstrate the value of light-client verification, modular application messaging and proof-based cross-chain state verification. TANGLE can use the same design principles while specializing the destination side around confidential state and privacy-native routing.

Design reference, not a dependency

Cosmos IBC is an example of modular interoperability built around on-chain light clients, state proofs and application modules. Polygon AggLayer is an example of proof-oriented interoperability that combines asset movement, messaging and cryptographic security. These systems inform the architecture; TANGLE is not specified as dependent on either system.

27 · RISKS & LIMITATIONS

Ambition requires honesty.

TANGLE is a research-driven architecture. The protocol does not claim that every proposed component has already been proven secure or production-ready.

Cryptographic risk

Incorrect cryptographic assumptions or implementation errors could compromise privacy or funds.

Economic risk

Insufficient liquidity, poor incentives or token volatility could reduce network security.

Network risk

A small or concentrated validator/routing set may create censorship or availability risks.

Regulatory risk

Privacy-oriented financial infrastructure may face different regulatory requirements across jurisdictions.

Adoption risk

A technically strong network can still fail if users, developers and liquidity providers do not adopt it.

Complexity risk

Recursive routing, confidential state and a dedicated L1 create substantial engineering complexity.

No absolute privacy guarantee

TANGLE's privacy objective is to reduce transaction correlation under explicit assumptions. It should not be interpreted as a promise of perfect anonymity against every possible observer.

28 · CONCLUSION

TANGLE is a network proposal.

The ambition of TANGLE is not to build another token with a privacy feature. It is to explore whether the transaction model itself can become a programmable, confidential and economically secured network primitive.

The proposed architecture combines a dedicated Layer-1, Proof-of-Stake security, protocol-native Routing Vaults, recursive fragmentation, randomized routing, confidential state, cryptographic commitments, zero-knowledge validity and a native economic asset.

TANGLE does not ask users to trust a promise of privacy. The architecture is designed to make privacy part of the protocol itself.
Architecture status

TANGLE L1, its consensus stack, cryptographic construction, Routing Vault custody model and several economic parameters remain proposed and under research. Mainnet deployment should follow implementation, adversarial testing, independent security review and cryptographic audit.
